## 1. 目的・背景

1件ずつの検索・スキャン・画像認識に加えて、**BGG上の自分の所持コレクションをまとめて取り込む**経路を追加する。これにより初期投入が一気に進み、分析ダッシュボード（Phase 2）も実データで映える。新しい解析方式は導入せず、取得した各ゲームは**既存の登録動線（thing取得→パース→upsert）にそのまま流す**。

### 1.1 設計の前提

- **BGGコレンションAPIは所持一覧（objectid群）を返すだけ。** 各ゲームの詳細（メカニクス・重さ等）は既存の `registerBggId`（thingエンドポイント）で取得・登録する。つまり本フェーズは「コレクション取得＋既存登録動線への一括投入」。
- **コレクション取得には BGG ユーザー名が必要。** Bearerトークン（既存・thing登録で使用）とは別物なので、**BGGユーザー名を設定に追加**する（非機密）。
- **既存のレート制限・リトライ・202再取得を必ず流用。** コレクション取得も thing 取得もBGGの規約内で行う（独自に速度を上げない）。BGGの `collection` エンドポイントは生成待ちで **202** を返すことがあるため、既存の202再取得（C-07）を使う。
- **重複は再取得しない。** 既に登録済みのゲーム（`AlreadyExists`）はスキップする（再実行で安全＝冪等・再開可能）。
- **自動実行しない。** ユーザーがユーザー名を確認し、取得→プレビュー→「インポート開始」を明示操作した場合のみ実行。途中キャンセル可能。

## 2. スコープ

### 2.1 含むもの（In Scope）

- FR-3-01 BGGユーザー名の設定保存（S-05、非機密）
- FR-3-02 コレクション取得（`collection` API、所持のみ＝`own=1`／`subtype=boardgame`、202再取得対応）
- FR-3-03 取得結果のプレビュー（総数・新規/既登録の内訳）
- FR-3-04 一括インポート（各 objectid を既存 `registerBggId` に投入。進捗表示・既登録スキップ・途中キャンセル・連続失敗中断）
- FR-3-05 インポート結果サマリ（登録 n / スキップ m / 失敗 k）と失敗時UX

### 2.2 含まないもの（Out of Scope）

- BGGコレクションの評価・コメント・プレイ回数の取り込み（本フェーズは「所持ゲームの登録」に限定）
- アプリ→BGG への書き込み（コレクション更新の双方向同期）
- 差分同期・自動定期同期（手動の一括取り込みのみ）
- スキーマ変更（ユーザー名設定の追加を除く）
- 対象プラットフォームの拡大（iOS/Desktop/Web）。**Android のみ**

## 3. 対象・非機能要件

| 項目 | 方針 |
|---|---|
| 対象OS | **Android のみ**（既存踏襲） |
| API | 既存 `BggApiClient` を拡張（`collection` 追加）。レート制限・リトライ・202・キャッシュは既存実装（C-01〜C-09）を流用 |
| 認証 | thing登録は既存どおりBearerトークン前提（未設定は既存の誘導）。コレクション取得はBGGユーザー名が必要 |
| 機密 | トークン/キーは既存 secure storage。**ユーザー名は非機密**として設定保存（settingsテーブル等） |
| 実行時間 | 大規模コレクションは thing 取得がレート制限（C-01: 15req/分）で数分かかりうる。進捗・キャンセル・再開（既登録スキップ）で対処 |
| オフライン | オンライン必須。オフライン時は取得不可を表示 |
| i18n | 追加文言はすべて `assets/i18n/{ja,en}.json` のキー経由（ハードコード禁止） |

## 4. 取得仕様

- エンドポイント: BGG XML API2 `collection`（既存のドメイン方針に従う。`www` を付けない）。
- パラメータ: `username={ユーザー名}` 必須、`own=1`（所持のみ）、`subtype=boardgame`（既定）。
- 202応答: 生成待ち。既存の202再取得（C-07: 3秒×最大3回）で待機・再取得。なお最終的に得られないときはタイムアウトとして扱い、再試行を促す。
- 解析: `<item objectid="...">` から **objectid（=BGG ID）** と name、yearpublished を抽出。所持判定は `own=1` 取得で担保。
- 後段: 抽出した objectid のうち**未登録**のものを既存 `registerBggId` に順次投入。`AlreadyExists` はスキップ。

## 5. 画面要件

### 5.1 S-05 設定（拡張）

- 既存のトークン/Geminiキーに加え、**BGGユーザー名**入力欄を追加（保存/クリア、設定済み/未設定表示）。

### 5.2 S-10 BGGインポート画面（新規）

- ユーザー名の確認（未設定なら設定へ誘導）。
- 「コレクションを取得」ボタン（202待機中はその旨を表示）。
- 取得結果プレビュー: 総数、**新規 / 既登録** の内訳。
- 「インポート開始」ボタン → 進捗（n/total、現在のタイトル）、**キャンセル**ボタン。
- 完了サマリ: 登録 n 件 / スキップ（既登録）m 件 / 失敗 k 件。失敗一覧（任意）。
- 既登録スキップ・途中キャンセル・連続失敗中断に対応。

### 5.3 導線・既存再利用

- S-01 のFAB登録メニュー（または設定）に「BGGから一括取り込み」を追加し S-10 へ。
- 各ゲームの登録は既存 `BggRegistrationRepository.registerBggId(bggId)` を再利用（Created/AlreadyExists の判定もそのまま）。

## 6. 取り込みフロー

```
[S-10 BGGインポート]
   │ ユーザー名確認 ──未設定──> [S-05 へ誘導]
   │（トークン未設定も同様に S-05 誘導）
   ▼ 「コレクションを取得」
 collection API (own=1, subtype=boardgame)
   │  202 → 既存C-07で待機・再取得
   ├─ 取得失敗/タイムアウト ──> 再試行を促す
   ▼ objectid群を取得
 プレビュー（総数 / 新規 / 既登録）
   │ 「インポート開始」
   ▼ (未登録の各 objectid を順次)
 registerBggId(objectid)
   │  Created → 登録 +1
   │  AlreadyExists → スキップ +1
   │  失敗 → 失敗 +1（連続失敗が閾値で中断）
   │  （キャンセル要求で安全に中断）
   ▼ 全件処理後
 サマリ（登録 n / スキップ m / 失敗 k）→ [S-01 一覧へ]
```

## 7. 失敗時UX要件

| 状況 | 挙動 |
|---|---|
| ユーザー名未設定 | S-05 へ誘導 |
| トークン未設定 | 既存の設定誘導（thing登録に必要） |
| ネットワークなし | 取得不可を表示し、後で再試行 |
| 202が解消しない | 「BGG側で生成中。時間をおいて再試行」 |
| 個別ゲームの取得失敗 | スキップして継続（失敗件数に計上）。連続失敗が閾値で中断し部分結果を表示 |
| キャンセル | 進行中の登録を安全に止め、そこまでの結果を表示（既登録は保持） |
| 再実行 | 既登録はスキップされ、二重登録されない（冪等） |

## 8. 受け入れ基準（概要）

- 設定にBGGユーザー名を保存でき、未設定時はインポートが開始できず設定へ誘導される。
- `collection` 取得が 202→200 を正しく扱い、objectid 群を抽出する。
- 取得結果が 新規/既登録 内訳つきでプレビューされる。
- インポートで未登録のみ `registerBggId` に流れ、既登録はスキップ、進捗とキャンセルが機能する。
- 連続失敗で中断し、部分結果サマリが表示される。
- 再実行で二重登録されない（冪等）。
- 既存のレート制限・リトライ・202を流用し、独自に速度を上げない。
- `flutter analyze` 警告ゼロ、`flutter test` 全件パス。
- 実機（Android）でE2E（ユーザー名設定→取得→プレビュー→インポート→サマリ）が通る。
