## 1. 概要・対象範囲

Board Game Shelf は、所持しているボードゲーム・拡張を記録し、BGG（BoardGameGeek）のデータと連携しながら、検索・分析・プレイ記録までを1つのアプリで完結させる、個人利用を主眼とした非商用のボードゲーム管理アプリである。

- **対象プラットフォーム**: Android のみ。iOS/Desktop/Webはビルド・テスト・保守対象外。`ios/` はFlutterツール互換のため残している
- **技術スタック**: Flutter / Riverpod（状態管理） / drift（SQLite） / dio（HTTP）
- **運用・配布方針**: 個人利用・非商用。広告なし。BGG APIを利用するためGoogle Playには登録せず、APKも配布しない。ソースコードから手元の環境で起動して使う
- **ライセンス方針**: MIT（現時点でリポジトリに `LICENSE` ファイルはない）
- **APIキーの扱い**: BGGトークン・Gemini APIキーはすべて利用者自身が取得し、端末のセキュアストレージにのみ保存する（同梱しない、開発者のサーバーを経由しない）
- **コア価値**: ローカルDB＋BGG検索登録＋boardgame_analyzer互換のYAMLエクスポートが基盤。これに、バーコード/写真認識による登録経路、コレクション分析、プレイ記録、拡張管理、多言語化を順次積み上げてきた

## 2. 共通の非機能要件

| 項目 | 方針 |
|---|---|
| オフライン動作 | ローカルDBの参照・編集・検索・分析・YAMLエクスポートは完全オフラインで動作する。オンラインが必要なのはBGG検索/登録/一括取込、GameUPCバーコード照会、Gemini画像認識のみ |
| 明示操作の原則 | 外部API（BGG・GameUPC・Gemini）へのネットワーク送信は、自動実行・バックグラウンド実行を行わず、必ずユーザーの明示操作（ボタン押下）を起点とする |
| i18n | UI文言はすべて `assets/i18n/{ja,en}.json` 等のキー経由で参照する。ハードコード文字列を作らない（詳細は §7） |
| 機密情報 | BGGトークン・Gemini APIキーは `flutter_secure_storage` にのみ保存し、DBファイル・YAMLエクスポート・ログに出力しない |
| BGG API規約遵守 | レート制限（thing 15req/分・search 20req/分）・リトライ・202再取得・キャッシュ（詳細TTL48h・検索TTL24h）を遵守し、独自に高速化しない。BGG XML APIの利用は非商用ライセンスの範囲内とし、アプリ内にBoardGameGeekの出典クレジットを表示する |
| テスト容易性 | 時刻・乱数・ネットワークに直接依存するロジックを書かず、Clock/Random/Transport等の抽象を注入してユニットテストする |
| パフォーマンス | コレクション一覧・分析集計は、数百〜1,000件規模でもスクロール・初回表示がジャンクしないこと。DBアクセスはコレクション件数に比例した逐次クエリ（N+1）を発生させない（2026-06、パフォーマンス改修で是正済み。詳細は `docs/DEVELOPMENT_BRIEF.md` の運用改善節） |

## 3. ゲーム登録

### 3.1 BGGタイトル検索・手動登録（基盤機能）
- タイトル検索（exact一致トグル付き）→候補確認（名称・年・サムネイル）→詳細取得→登録、の流れ。
- 既存game_keyの再登録は新規行を作らず既存詳細へ遷移する。
- BGGトークン未設定時は検索実行前に設定画面へ誘導する。

### 3.2 ローカル独自レコード登録（同人ゲーム等）
- タイトルのみ必須の手入力フォーム。人数・時間・メカニクス（自由テキスト）・カテゴリは任意。
- ローカルIDは `L` + 5桁連番（`L00001`〜）。BGG再取得（情報更新）の対象外。

### 3.3 バーコードスキャン登録
BGG APIにはバーコード検索が存在しないため、JAN/EAN-13バーコードからの解決は次の4段フォールバックで行う（2026年のGameUPCオフラインキャッシュ追加により、当初の2段構成から拡張済み）。

1. **ローカル学習済み（`barcode_map`）**: 過去にこのアプリ内で確定登録されたJAN→ゲームの対応。オフラインで即座に解決する。
2. **GameUPCオフラインキャッシュ**: アプリに同梱・任意更新可能なGameUPCのCSVダンプ由来のローカルキャッシュ。ネットワーク不要で、ヒットすれば確定候補としてBGG登録に直接合流する。
3. **ライブGameUPC API**: オフラインキャッシュがミスした場合のみ、オンラインでGameUPCの照会APIを呼ぶ。確信度に応じて自動登録または候補選択（投票つき）。
4. **タイトル検索/手動登録**: 上記すべてがミスした場合の最終手段。登録成功時に `barcode_map` へ学習保存し、以後の同一JANスキャンを高速化する。

カメラ非対応・権限拒否時は手入力JANフォームにフォールバックする。受理形式はEAN-13（ISBN-13含む）。UPC-Aは先頭0付与で正規化。同一JANの連続検出は多重登録を防ぐため一定時間抑止する。

### 3.4 箱表紙の写真認識
- 端末カメラ撮影またはギャラリー選択で箱表紙1枚を取得し、ユーザーの明示操作でのみGemini（マルチモーダル）に送信する。
- Geminiが返す推定タイトル（原語/日本語）・出版社・確信度はBGG IDを直接確定する用途には使わず、既存のタイトル検索のクエリとして渡し、候補確認→登録の通常動線に合流させる。
- 確信度が下限未満、抽出不能、キー未設定、ネットワークなしの場合は手動検索にフォールバックする。

### 3.5 棚全体の一括認識
- 棚画像1枚から複数ゲームを検出し（オブジェクト検出・クロップは実装しない。Geminiが返すJSON配列をそのまま使う）、一括レビューUIで確信度・既登録可能性を見ながら選別する。
- 選択分は1件ずつ既存のタイトル検索→候補確認→登録の動線に流し、登録済み/スキップ/未処理の状態を管理する。取りこぼし・誤検出が起こり得る前提でUIに明示する。

### 3.6 BGGコレクション一括取り込み
- 設定したBGGユーザー名（非機密）をもとに、BGGの `collection` API（`own=1`, `subtype=boardgame`）で所持ゲーム一覧（objectid群）を取得する。
- 各objectidは既存の `registerBggId`（thing取得→パース→upsert）にそのまま投入する。新しい解析・登録経路は作らない。
- 既登録はスキップ（冪等）。進捗表示・キャンセル・連続失敗（5件）での中断に対応する。

### 3.7 拡張（Expansion）の検出・登録
- BGGの `link type="boardgameexpansion"` リンクから、登録対象アイテムが拡張か基本ゲームかを判定し、`games.gameKind`（`base`/`expansion`）・`parentGameKey`（親のBGG ID）を設定する。
- 新規ベースゲーム登録直後に、未登録の拡張候補を一覧提示し、個別に登録できる（任意・スキップ可能。新規追加のAPIコールは発生しない）。
- 親未登録の拡張は登録でき、詳細画面から「親ゲームを登録」操作で後から解消できる（`parentGameKey` にFK制約は設けない）。

## 4. コレクション管理

### 4.1 一覧画面
- リスト/グリッド表示の切り替え、タイトル部分一致検索（表示言語に関わらず全言語名を対象に検索、§7.2参照）。
- フィルタ: 人数・時間・ローカルのみ・メカニクス（複数選択・OR一致）・デザイナー（複数選択・OR一致）・拡張あり・未プレイ。メカニクス/デザイナーの選択肢は「自分のコレクションに存在する値」の和集合（BGG全体の語彙ではない）。
- ソート: 五十音順（表示名基準）・デザイナー順・最終プレイ日が古い順（未プレイは最古扱いで先頭）。
- 拡張は親（基本ゲーム）の直下にインデント表示する（リスト表示のみ。グリッドは拡張バッジのみ）。親が一覧に存在しない拡張は単独表示＋「親ゲーム未登録」バッジ。

### 4.2 詳細画面
- BGG由来データは読み取り専用。所持メタデータ（owned / acquired_date / condition / storage_location / memo / purchase_price）は編集可能。
- 「情報更新」操作でBGGを再取得し、差分（数値は1e-6の許容誤差、mechanics/categories等は追加/削除を列挙）を確認のうえ上書き・`update_history` に記録する。所持メタデータ（collectionテーブル）はこの更新の影響を受けない。
- 「拡張情報」セクション: 拡張なら親ゲームへのリンクまたは登録ボタン、基本ゲームなら登録済み拡張の一覧。
- 「分析」セクション（§5.2）は拡張では非表示にし、案内文に置換する。
- 「プレイ記録」セクション（§6.1）は基本ゲームのみで機能し、拡張では案内文のみ。
- 削除は所持メタデータ入力済み、またはプレイ記録が存在する場合に確認ダイアログを必須とする。

## 5. 分析・ダッシュボード

### 5.1 コレクション分析ダッシュボード
完全オフライン・読み取り専用で、DBへの書き込みは一切行わない。

- 概要指標（総所持数、BGG由来/ローカル内訳、平均重さ・平均評価〔欠損除外＋除外件数明示〕、購入価格合計）
- 分布（重さ・プレイ時間・発売年代・評価）、人数カバレッジ（1〜8人）
- 上位ランキング（メカニクス／カテゴリ／デザイナー／パブリッシャー Top-N）
- 保管場所別カウント・入手時期の推移
- 基本ゲーム数／拡張数の内訳
- 分析対象トグル（所持中のみ／全レコード）

### 5.2 多次元分析指標（boardgame_analyzer純Dart移植）
姉妹プロジェクト boardgame_analyzer の算出ロジックを忠実に移植したもの。係数・分岐は移植元が正本であり、独自チューニングはしない。

- 算出指標（各1.0〜5.0）: 初期障壁・戦略的深度・リプレイ性・意思決定点・相互作用複雑度・ルール複雑度・メカニクス複雑度・ソロ適性・人数スケーラビリティ・運依存度
- 分類: 学習曲線タイプ（9種）・プレイヤータイプ・習熟時間（4段階）
- 重み付けデータ（`mechanics_data.yaml` / `categories_data.yaml` / `rank_complexity.yaml`）はアセット同梱・読み取り専用。未知名称は既定値にフォールバックし、書き戻さない。
- 拡張（`gameKind == 'expansion'`）にはこの指標を算出・表示しない（基本ゲームに対してのみ算出）。
- 完全オフライン・決定的（「現在年」のみClock注入で制御）。

## 6. プレイ記録・プレイ傾向分析

### 6.1 プレイ記録
- 記録対象は基本ゲームのみ（`gameKind != 'expansion'`）。拡張はそのプレイで「使用した拡張」として複数選択で記録する。
- 記録項目: 日付（必須）、プレイ人数、実プレイ時間、使用した拡張（登録済み拡張からのみ選択）、評価（1〜10、BGG評価と同尺度）、また遊びたい度（1〜5）、重さの体感（1.0〜5.0・0.5刻み、`games.weight`と同尺度）、感想メモ、勝者・スコアの自由記述。
- v1では追加・削除のみ（編集機能はなし。修正は削除して再登録）。
- ゲーム削除時、紐づくプレイ記録・使用拡張記録はカスケード削除される。プレイ記録が存在するゲームの削除は確認を必須とする。

### 6.2 「遊ぶゲームを探す」絞り込み
§4.1のフィルタ（メカニクス・デザイナー・拡張あり・未プレイ）・ソート（最終プレイ日が古い順）として実現。専用の「探す」画面は作らない。

### 6.3 プレイ傾向分析ページ
プレイ記録に基づく独立した分析ページ（コレクション構成を扱う§5.1のダッシュボードとは別）。

- プレイ記録数、実プレイ時間の平均・分布、実プレイ時間と公称時間（`games.playingTime`）の差分平均
- よく遊ぶメカニクス／デザイナー、評価が高いメカニクス／デザイナー（平均・件数併記）
- 拡張の使用回数、プレイ人数別の平均評価
- 「最近遊んでいないお気に入り」（平均評価7点以上〔10点満点〕で最終プレイ日が古い順）
- 「プレイ人数×ゲーム」マトリクスや経年トレンド、勝率集計は対象外（個人のデータ量では統計的意味が薄いため）

## 7. 多言語化

### 7.1 UI言語切り替え
- `assets/i18n/` 配下のJSONを実行時に動的列挙し、追加するだけで設定画面の選択肢に出る（`AssetManifest` 経由）。
- 既定は「システムに従う」。手動選択も可能で、選択は即時にUIへ反映され、再起動後も保持される（`shared_preferences`に保存。秘密情報ではないためセキュアストレージとは分離）。
- システム言語が未対応言語の場合は英語にフォールバックする。

### 7.2 ゲーム名のUI言語連動表示
- 表示名はUI言語に連動する（日本語UI→日本語名優先、英語UI→英語名優先）。該当言語の名称が無いゲームは英語名（primary）にフォールバックする。
- 検索は表示言語に関わらず、登録されている全言語名（primary/japanese/english/alternates）を対象にする（表示言語を変えても検索ヒットが狭まらない）。
- ソートは表示名（言語連動後の値）基準。

## 8. データ管理

### 8.1 YAMLエクスポート
- boardgame_analyzerの `game_data/*.yaml` と同一キー構成・出現順序を保証する（互換性が最優先）。個別/一括出力に対応し、一括時は内容ハッシュで無変更レコードをスキップする（全件出力オプションあり）。出力済みハッシュは全ファイルの保存成功後に更新し、保存失敗時は次回も出力対象とする。
- ファイル名はBGG由来 `{6桁ゼロ埋めID}_{名称}.yaml`、ローカルは `L{5桁}_{名称}.yaml`。
- 本アプリ独自の所持情報は `collection:` ブロックとして付加する（boardgame_analyzer側は無視できる）。

### 8.2 バックアップ
- 設定画面から手動バックアップ（`backup_YYYYMMDD_HHMMSS.sqlite`）をアプリのドキュメント領域内の `bg_shelf_backups/` に保存する。
- 自動バックアップの命名処理（`YYMMDD.sqlite`）はあるが、自動実行は未実装。アプリ内の復元機能も未実装。

### 8.3 設定
- BGGトークン・Gemini APIキー（セキュアストレージ）。
- BGGユーザー名（非機密、一括取込用）。
- UI言語（§7.1）。
- GameUPCオフラインキャッシュの状態表示・手動更新（§3.3）。
- データ提供元（BoardGameGeek・GameUPC）のクレジット表示は要件だが、現在の設定画面には未実装。

## 9. 削除済み・対象外の機能（重要な注記）

- **Gemini翻訳機能（説明文の日本語翻訳）**: Phase 0設計時点では実装範囲に含まれ、Gemini APIキーは「翻訳とVision機能の共用」という位置づけだった。**2026年6月の改修で完全に削除**され、現在Gemini APIキーは画像認識（箱写真・棚写真）専用。`Games.descriptionJa` カラムはデータ保護のため残しているが、書き込み経路はない。説明文そのものの表示（原文・翻訳問わず）も現在は提供していない。
- **拡張への分析指標算出・基本＋拡張の合成評価**: 対象外（§5.2参照）。
- **プレイヤー別スコア・勝敗の構造化記録**: 対象外（`winnerMemo`の自由記述のみ）。
- **iOS/Desktop/Web対応の拡大**: 対象外（ビルドを壊さない範囲に留める）。

## 10. データモデル概要（参考）

主要テーブル（詳細スキーマは `lib/src/data/db/app_database.dart` が正）:

| テーブル | 役割 |
|---|---|
| `games` | BGG由来/ローカルのゲームマスタ。`gameKind`/`parentGameKey`で拡張の親子関係を表現 |
| `collection` | 所持メタデータ（1ゲーム1行、`games.gameKey`に対応） |
| `barcode_map` | ユーザーが確定登録したJAN→ゲームの学習済み対応 |
| `gameupc_cache` | GameUPC CSVダンプ由来のオフラインバーコード解決キャッシュ |
| `play_sessions` / `play_session_expansions` | プレイ記録と、そのプレイで使用した拡張の関連 |
| `api_cache` | BGG APIレスポンスのキャッシュ（TTL付き） |
| `settings` | 非機密設定（BGGユーザー名、各種メタ情報等） |

API/鍵類（DBやエクスポートに含まれない）は `flutter_secure_storage` 経由で別管理する。
